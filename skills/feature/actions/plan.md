# Plan features from the overview

1. Use the owner's requested scope and read `context/project-overview.md`. Read existing specs and the active record to avoid duplicating or replacing work. Before writing specs, verify that the intended overview, shared setup files, and selected screenshots are committed on local `dev`. A file that exists only in the working tree or index is still pending. If planning inputs are missing or only the old versions are committed, name the affected paths and wait for the owner to record the intended inputs. Preserve unrelated edits.
2. For a full roadmap that includes browser UI, or a request scoped to browser UI, check **Visual references** in the overview and inspect the linked files in `context/screenshots/` before writing specs. A folder link, `.gitkeep`, or a `Pending` entry does not count as a reference. Proceed without references only when the owner explicitly requests it for the scope being planned. A bare `N/A`, delegated visual choices, and general approval of recommendations do not establish that decision. If the visual step is pending, explain what is missing and return to the relevant step for choosing or supplying references. Projects without browser UI and requests explicitly scoped to work independent of the UI can proceed without this step.
3. Turn the agreed outcomes into independently verifiable pieces of work. Respect milestones, dependencies, and product non-goals. Assign each feature to an agreed milestone. If the milestone or required behavior is unclear, report the open decision and continue with specs whose scope and milestone are clear once the applicable reference step is complete.
4. Write one Markdown spec per feature in English in `context/features/`, including titles, section headings, and acceptance criteria. Keep localized UI strings as quoted examples when needed. Use the filename format `m<milestone>-<sequence>-<slug>.md`, for example `m0-01-baseline-check.md` or `m1-02-date-only-conversion.md`.
   - Use the lowercase milestone ID from the overview, such as `m0` for `M0`.
   - Number specs in the intended implementation order within each milestone. Start at `01` for each new milestone and pad numbers below `10` with a leading zero. When adding to an existing milestone, continue after its highest assigned sequence and keep existing IDs stable.
   - Use a short, descriptive kebab-case slug. Use the full filename stem as the spec ID in workflow requests.
   - Give each spec an outcome, scope, dependencies, acceptance criteria, and verification cases. Refer to relevant domain rule IDs and flows. For UI scope, link the exact screenshot files from the spec and explain which screen, state, or design detail they illustrate. Use the overview for behaviors and requirements. When the owner asks to refresh specs after reviewing references, update the affected specs in place and preserve their IDs.
   - For an explicitly requested fix spec, use a short kebab-case ID in `context/fixes/` and include reproduction steps and the expected result in English.
5. Link each feature spec to its Markdown file from the corresponding roadmap entry. Report the files, recommended order, and open decisions. Planning changes documentation only and leaves the active feature record alone.
